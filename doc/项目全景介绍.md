# Dzint Nexus 平台（dzint-agent-server）项目全景介绍

> 文档版本：v1.0（2026-09-04）
> 面向读者：技术团队、新成员、评审与决策层
> 基座：芋道（yudao-boot）脚手架，版本 2026.06-jdk25-SNAPSHOT

---

## 一、这个项目是做什么的

**一句话定位**：一套面向制造业的 **多租户 SaaS 智能体平台**——以 AI Agent 能力为核心引擎，向下打通 MES（制造执行）、WMS（仓储管理）、BPM（流程审批）、CRM/ERP 等业务域，向上通过 Hub 前台和运营分析实现商业化交付。

几个关键事实：

| 事实 | 说明 |
|------|------|
| 服务名 | `dzint-agent-server`（配置于 application.yaml） |
| 生产库 | `dzint-nexus-pro`（产品线代号 Nexus） |
| 技术基座 | 芋道 yudao-boot 单体多模块架构（Maven 聚合工程） |
| 运行形态 | 单体部署、模块化组装：`yudao-server` 按需聚合各业务模块 |

平台的演进思路可以概括为三层：

1. **底座层**：芋道框架提供的 SaaS 基础能力——多租户、RBAC 权限、数据权限、工作流、基础设施（文件/任务/监控/代码生成）。
2. **业务层**：MES / WMS / CRM / ERP / BPM 等垂直业务模块，当前 MES 是业务侧最重的资产。
3. **智能层（差异化所在）**：AI 模块（大模型接入、知识库 RAG、可视化工作流、数据资产管线）+ Analytics 运营分析 + Hub 商业交付前台。这是项目区别于"又一个 ERP/MES 二开"的核心。

## 二、总体架构

### 2.1 技术栈（相当激进）

| 维度 | 选型 |
|------|------|
| 语言/运行时 | **Java 25** |
| 框架 | **Spring Boot 4.1.0**（Jakarta 生态） |
| ORM | MyBatis-Plus（Spring Boot 4 starter）+ MyBatis-Plus-Join（联表）+ 动态多数据源 + Druid 连接池 |
| 缓存/会话 | Spring Data Redis |
| 工作流引擎 | Flowable（BPM 模块） |
| 实时音视频 | LiveKit（PoC 阶段，为语音/视频 Agent 铺路） |
| 构建 | Maven + flatten-maven-plugin 统一 revision 版本 |
| 数据库兼容 | MySQL 为主，SQL 脚本覆盖 PostgreSQL / Oracle / SQLServer / DM（达梦）/ KingBase / HighGo / OpenGauss / DB2 九种，国产化适配到位 |

JDK 25 + Spring Boot 4.1 的组合在国内业务系统里属于第一梯队，代价是需要持续跟进上游 API 变更（工程里已为此做了 compiler 参数与 starter 适配）。

### 2.2 工程结构

```
yudao（聚合根 POM）
├── yudao-dependencies          # BOM：全工程依赖版本统一管理
├── yudao-framework             # 15 个自研 Spring Boot Starter（技术中台）
│   ├── web / security / mybatis / redis / mq / job / excel / websocket
│   ├── monitor / protection / test / common
│   └── biz-tenant / biz-data-permission / biz-ip   # SaaS 三件套
├── yudao-server                # 启动器：聚合装配所有启用的模块
├── yudao-module-system         # 租户/用户/角色/部门/字典（SaaS 底座）
├── yudao-module-infra          # 代码生成、文件、定时任务、监控
├── yudao-module-bpm            # Flowable 审批流
├── yudao-module-crm / erp      # 标准 CRM / ERP
├── yudao-module-mes            # ★ 制造执行系统（369 个 Java 类，8 大域）
├── yudao-module-wms            # ★ 独立仓储管理（开发中）
├── yudao-module-ai             # ★ AI 模块（重构为 6 子模块）
├── yudao-module-analytics      # ★ 平台运营分析（跨租户全局统计）
└── yudao-module-hub            # ★ 用户前台与商业交付聚合模块（骨架）
```

带 ★ 的五个模块是本项目在芋道开源基座之上的自研增量，也是投入的重心。

### 2.3 架构分层约定

数据访问遵循仓库内《数据存储层开发手册》的强约束：

- 调用链：`Controller → Service → Mapper(MySQL) / RedisDAO(Redis)`；
- 所有 DO 继承 `BaseDO`，自动获得 5 个审计字段（creator/updater/createTime/updateTime/deleted），由 `DefaultDBFieldHandler` 自动填充，逻辑删除全局拦截；
- Mapper XML 统一放 `resources/mapper/{业务域}/`，与接口包名对应；
- 金额统一 `BigDecimal`（单位元）。

## 四、已实现的核心链路

### 4.1 生产执行闭环（MES，最核心资产）

```
主数据(md) ──► 工艺路线 ──► 工单 WorkOrder ──► 生产任务 Task ──► 派工 TaskIssue
 (物料/工作站)   (route+process)   │                  │
                                  ▼                  ▼
              质量检验 qc ◄──── 报工 Feedback ──► 更新任务/工单产量
              (IQC/IPQC/OQC/RQC)   │
                                  ▼
                    物料消耗 ItemConsume + 成品产出 ProductProduce
                                  │
                                  ▼
                    成品入库 / 发货 / 销售（wm 域）
```

关键实现（代码已核实）：

- **工单状态机**：草稿 → 已确认 → 已完成 / 已取消；草稿才可编辑/删除，已确认才可完工/取消，非法状态操作直接抛业务异常；
- **任务创建强校验**：任务必须挂接有效的工单 + 工艺路线 + 启用状态的工序，客户信息自动从工单继承；
- **报工事务链（亮点）**：一次报工在事务内联动四件事——① 生成物料消耗单并结算，② 生成成品产出记录，③ 回写任务累计产量，④ 回写工单累计产量；
- **质量闭环**：检验模板 → 四层检验单 → 缺陷记录 → 检验指标结果，待检池统一调度。

### 4.2 仓储库存链路（双轨）

MES 内嵌 wm 域覆盖车间级物流（24 个子域，从到货通知到库存事务台账），独立 WMS 模块走的是另一条产品化路线：

```
入库单(草稿) ──complete──► 执行：明细逐条落账 ──► changeInventory(事务)
                │                                   ├── 库存表增减
                │                                   └── 库存流水(历史)记录
                └──cancel──► 作废（仅草稿可作废）
```

- 单据模型四类：**入库 Receipt / 出库 Shipment / 移库 Movement / 盘点 Check**，共用统一状态机（草稿 0 → 已完成 4 → 已作废 5）；
- 库存服务提供 `changeInventory`（变动）与 `checkInventory`（盘点校对）两个事务入口，所有单据完成动作最终收敛到这两个入口，账实一致有保障；
- 独立 WMS 的四类单据 Service 层已实现（含仓库/商家/物料/SKU 主数据校验），订单域的 DO/Mapper/Controller 尚未入库，属于明确的 WIP。

### 4.3 AI 智能层链路（差异化能力）

虽然 AI 模块 Java 源码尚未同步进本仓库，但从数据库 DDL、Mapper XML、子模块划分与脚本可以完整还原设计：

**(1) 大模型接入与对话**：已接入通义千问、文心一言、讯飞星火、智谱 GLM、DeepSeek 等；core 子模块承载模型管理、对话/会话、Agent、工具、Token 统计。

**(2) 知识库 RAG**：knowledge 子模块（Wiki / WikiCatalog / Document / DocumentContent / Knowledge 五张表的 Mapper 已就位），文档入库→切片→向量化→检索问答。

**(3) 可视化 AI 工作流（对标 Dify）**：`ai_workflow` 表存储画布数据（`graph` JSON：nodes+edges）与发布快照（`published_graph`），带版本号自增、草稿/发布/下架状态机、使用次数统计；`ai_workflow_run` 记录每次运行。**编辑与运行隔离的快照式发布**是正确且难得的工程设计。

**(4) AI 数据资产管线**：`ai_data_*` 六张表构成"数据源配置 → 采集任务 → 采集结果 → 数据资产（+内容）→ 治理记录"的完整链路，为 Agent 提供可信数据供给。

**(5) 配套工程**：`mermaid-validator`（Node 校验服务，配合 core 内置的 32 类 Mermaid 语法知识，支撑 AI 生成架构图/流程图的正确性校验闭环）；`livekit-poc`（LiveKit 自部署 PoC，webhook 回调后端 `/admin-api/im/livekit/webhook`，为实时语音/视频 Agent 铺路）。

### 4.4 SaaS 运营分析链路（Analytics）

analytics 模块通过 `@TenantIgnore` 关闭租户隔离，做**平台级跨租户统计**：

- 总览：用户/部门/岗位数、租户数、AI 模型数、知识库数、Agent 数、文档数、**Token 总消耗**、文件数、任务数；
- 按租户聚类统计（无数据的租户也保证展示）；
- AI 能力盘点（模型/Agent/工具/技能/Wiki/文档/工作流）与 AI 用量分析。

这条链路把"平台运营视角"和"租户业务视角"分开，是商业化 SaaS 的正确姿态。

## 五、亮点提炼

**架构与工程**

1. **技术栈前瞻**：JDK 25 + Spring Boot 4.1 + Jakarta，国内业务系统里第一梯队；九种数据库方言脚本（含达梦/人大金仓等国产库），国产化投标无障碍。
2. **可插拔模块化**：业务模块是否参与部署只取决于 `yudao-server` 的依赖清单，裁剪、按客户组装都很轻。
3. **框架 Starter 化中台**：15 个自研 starter 把租户、数据权限、安全、ORM 等横切能力下沉，业务模块保持薄。
4. **数据层强规范**：BaseDO 统一审计字段 + 自动填充 + 全局逻辑删除 + 金额单位约定，且有正式的开发手册约束（仓库 `doc/数据存储层开发手册.md`），新人上手成本低。

**业务设计**

5. **MES 域建模完整且克制**：369 个类覆盖主数据到看板的制造闭环，四层质量检验（IQC/IPQC/OQC/RQC）+ 安灯 + 班次日历 + 设备点检保养，对中小制造企业是完整方案。
6. **报工事务链**：一次报工事务内联动产量回写、物料消耗、成品产出，账物同步不靠事后对账。
7. **WMS 单据-库存收敛设计**：四类单据全部收敛到 `changeInventory/checkInventory` 两个事务入口，是防止库存超卖/账实分离的正确做法。

**AI 与平台**

8. **AI 模块分层重构**：从单体重构为 common/core/knowledge/search/data 六子模块，按领域解耦，为后续独立演进留了空间。
9. **快照式工作流发布**：graph 与 published_graph 分离 + 版本自增，运行中的实例不受编辑影响——这是很多自研工作流踩过坑才学会的设计。
10. **AI 生成内容校验闭环**：Mermaid 语法知识内置 + 独立校验服务，AI 出图先验证再交付。
11. **跨租户运营分析**：Analytics 模块天然站在平台方视角，Token 消耗、AI 能力利用率可量化，SaaS 计费与成本管控有数据底座。

## 七、总结

这不是一个简单的"芋道二开"，而是一次**以 AI Agent 为差异化引擎、以制造业 SaaS 为落地场景的平台工程**：

- 短期价值已经兑现：MES 生产闭环可用，是当前最能打业务单的资产；
- 中期看 AI 三件套（知识库 RAG + 可视化工作流 + 数据资产管线）与 Analytics 的组合，构成"智能平台"的骨架；
- 长期看 Hub 的商业化交付能力决定这套东西能否从"项目"变成"产品"。

技术底座新、模块边界清晰、规范文档化，底子是好的；当前主要矛盾在**收口**——WMS 补全、AI 源码归位、Hub 立项，三条线收口后即可形成完整叙事。
